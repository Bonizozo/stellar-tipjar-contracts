# SDK Interface Drift Audit

## Findings

`sdk/src/lib.rs` is not a client binding. It is an empty Rust library kept as
a workspace member and has no contract methods, generated code, or public
interface that can drift from the deployed contract.

The hand-written client is the TypeScript implementation under
`sdk/typescript/src/`. It is not spec-generated. Its public calls already
show interface drift from the current `contracts/tipjar` source: `tip` omits
the required `token` argument, and `withdraw` uses a four-argument payout
shape that is not the contract entrypoint's current signature. The supporting
types and event parsing are hand-maintained as well.

`packages/contract-client/src/generated.ts` is a separate client and is
generated by `stellar contract bindings typescript` through
`scripts/generate-bindings.sh`. That is the appropriate client surface for
new integrations, but the checked-in file is vendored output from a deployed
contract ID. Before this change it was neither regenerated nor compared in
CI. Its current four-method spec also differs from the current contract
source, so it must not be treated as proof that the hand-written SDK is
current.

## Decision

Do not add a second hand-maintained Rust binding layer. The Rust crate should
either remain an explicitly documented placeholder or be removed from the
workspace when no Rust client is needed.

For the TypeScript client, use spec-driven bindings as the public API. Build
the contract WASM in CI, run `stellar contract bindings typescript --wasm`
against that artifact, and compare the generated API with the checked-in
`packages/contract-client/src/generated.ts`. This catches renamed methods,
argument changes, return-type changes, and removed or added entrypoints
without relying on a deployed network or a mutable contract ID.

The CI check compares only the generated `Client` declaration, excluding
network and deployment metadata. Until the vendored artifact is regenerated
from the intended deployed version, CI will fail and `sdk/typescript` and
`packages/contract-client` must be treated as separate, potentially
incompatible clients. Downstream integrators should use the generated client
and pin it to the contract WASM version they deploy against.

## Verification commands

```bash
cargo build -p tipjar --target wasm32v1-none --release
scripts/check-contract-client-drift.sh \
  target/wasm32v1-none/release/tipjar.wasm
```

The check fails when the callable interface differs from the checked-in
generated client.

To repair a drift failure after deciding which contract version is canonical:

```bash
TIPJAR_WASM=target/wasm32v1-none/release/tipjar.wasm \
  scripts/generate-bindings.sh
```
